# M3.5 性能ゲート: TLC との速度比

M3.5 では、M3 までに作った 1 worker の探索が TLC と比べてどれだけ遅いかを tlaplus/Examples の大きめのモデルで測り、DESIGN.md が受け入れた表現 (`Arc` の cons list と動的 lookup) のままで進めてよいかを決める。この文書は合格基準、計測の条件と結果、比べられなかったケースを記録する。

## 合格基準

DESIGN.md は「許容できなければ表現を見直す」とだけ書き、数値を決めていなかった。M3.5 の着手時に次の基準を決めた。

- 比べられるケースの壁時計時間の比 (tlars / TLC) の幾何平均が 3 倍以内。
- どのケースも 5 倍以内。

基準の相手は JIT の効いた TLC で、比は 1 worker どうしで取る。並列化は M6 で入るので、ここでの比は 1 worker の評価器と探索の速さだけを表す。

## 計測の条件

- 対象は `bench/suite.txt` の cfg で、`cargo run --release -p xtask -- bench run --engine tlc|tlars` で 1 回ずつ流した。状態数は Examples の manifest と照合し、表のケースはすべて一致した。
- ホストは chansuke (24 コア)。TLC は `nix build .#tlc` の bc1b506、JDK 21、既定のヒープ、`-XX:+UseParallelGC` である。TLC の結果は `bench/baselines/tlc-bc1b506-jdk21-w1-chansuke.jsonl` に置いた。carbon の基準値とはホストが違うので、TLC もこのホストで取り直した。
- 起動時間がほとんどを占める Chameneos (TLC 1.0 秒、tlars 0.5 秒) は、比が評価器の速さを表さないので幾何平均に入れない。

## 結果

| モデル | TLC | 着手時の tlars | 完了時の tlars | 比 |
|---|---|---|---|---|
| PaxosCommit | 108.5 s | 581 s | 312.4 s | 2.88× |
| MCLamportMutex | 12.7 s | 47.6 s | 32.5 s | 2.55× |
| MCNanoMedium | 16.9 s | 163 s | 38.4 s | 2.27× |
| MultiPaxos_MC_small | 18.1 s | 停止 (不具合) | 51.2 s | 2.82× |
| SlushSmall | 6.2 s | 20.7 s | 13.4 s | 2.15× |
| TLCSailfish1 | 37.8 s | 900 s で打ち切り | 93.3 s | 2.47× |
| GameOfLife | 10.5 s | 83.7 s | 29.5 s | 2.80× |

完了時の幾何平均は 2.55 倍、最悪は PaxosCommit の 2.88 倍で、基準を満たした。最大常駐メモリは tlars のほうが少なく、PaxosCommit では tlars 606 MB、TLC 5.7 GB である。

着手時の計測で、MultiPaxos と Sailfish は正しさの不具合で止まるか、極端に遅かった。どちらも TLC と挙動が違う不具合だったので、速度より先に直し、TLC と照合する spec の golden を 1 件ずつ足した。

- SelectSeq、SortSeq、BagOfAll に渡した演算子が、状態変数を読むと未定義になっていた。TLC の `OpLambdaValue` は作られたときの状態を持つが、tlars は空の状態で本体を評価していた。
- INSTANCE したモジュールの名前付き `ASSUME` を名前で使うと未定義になっていた。TLC は ASSUME、Init、Next、ENABLED の 4 か所で `ThmOrAssumpDefNode` の本体を展開する。

## 速度の差はどこにあったか

速度の改善は、プロファイル (`perf record`、frame pointer 付きの `profiling` ビルド) で比の大きいケースから順に原因を特定して進めた。効果の大きかった順に並べる。

- **LazyValue のキャッシュ判定。** TLC の `TLCState.isSubset` は `Objects.equals` で値を比べるので、同じオブジェクトなら中身を比べない。tlars は毎回値を深く比べており、これが Sailfish の 40 倍の原因だった。同じ `Arc` なら比較を省き、完全な状態のスナップショットは値を写さず共有するようにした。
- **割り当て。** 遅延評価は束縛ごとに文脈のセルと thunk を作り、TLC はこれを JVM のヒープで安く確保する。アロケータを mimalloc に替えると多くのケースで 15〜25% 縮んだ。
- **SYMMETRY の置換。** 何も動かない値でも配列を確保して全要素を写していた。最初に要素が変わった時点で写すようにした (MultiPaxos)。
- **評価のたびの小さな費用。** `EvalError` を Box にして評価結果を 2 語にし、組み込み演算子の判定を名前の照合から表引きにし、レコードの欄名の文字列をエラーのときだけ作るようにした。グラフと引数の複製もやめた。

残る差の多くは、`lookup` が文脈の連結リストを辿るポインタ追跡 (Sailfish では `lookup` の自己時間の 7 割) と、値の参照計数である。どちらも DESIGN.md が忠実性の費用として受け入れたもので、基準を満たしたので arena 化はしない。並列化 (M6) の後にもう一度測る。

## 比べられなかったケース

`bench/suite.txt` の 15 件のうち、次の 6 件は liveness (M4) が要るので tlars が止まり、比べていない。

| モデル | 理由 |
|---|---|
| CoffeeCan1000Beans、ACP_SB_TLC、TokenRing、FastPaxos、AllocatorImplementation | cfg に `PROPERTY` がある |
| MCDisruptor_MPMC | `PROPERTY` はないが、SPECIFICATION に公平性条件 (`WF_vars`) があり、tlars はこれを liveness として止める |

M4 の完了後に、この 6 件を同じ手順で測る。

MCbtree は suite から外した。btree は CommunityModules の `Relation` を EXTENDS しており、suite の選定条件 (CommunityModules に依存しない) に合わない。このホストでは TLC も `Relation` が見つからずに止まる。carbon の基準値で TLC が通っている理由は確認していない。
