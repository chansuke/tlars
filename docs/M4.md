# M4 計画: 活性の検査

M4 では、TLC の活性の検査 (`tlc2.tool.liveness`) を Rust で書き、cfg の `PROPERTY` と SPECIFICATION の公平性条件を持つ仕様の検査結果を TLC の出力とバイト単位で一致させる。対象は、時相式を正規形に変えて tableau を作る式の側 (`Liveness.processLiveness`)、探索中に振る舞いのグラフを作る側 (`LiveCheck`)、終了時に強連結成分を調べて反例を組み立てる側 (`LiveWorker`) の 3 つである。この文書は作業の順序と完了条件を決め、進捗を記録する。

## 完了条件

- tla-ts のコーパスの次の対象について、tlars と TLC bc1b506 の終了コードと正規化した `-tool` 出力が一致する。照合は `xtask conformance run --check --suite S --context C` で行い、CI が全部の対象を流す。

  | スイート | 文脈 | 件数 |
  |---|---|---|
  | `temporal` | `model` | 827 |
  | `expressions` | `property` | 922 |
  | `checker` | `model` | 821 (M3 の 808 件に、`PROPERTY` を持つ 13 件を加えた数) |
  | `standard` | `model` | 96 (M3 の 92 件に 4 件を加えた数) |

- M3 の 10 対象は全件合格のままである。
- 照合の記録はすべて `-lncheck final` で取られている。探索の途中で活性を調べる経路 (`LiveCheck.check` の閾値による検査) はコーパスでは通らないので、M4 では探索の終わりの検査 (`finalCheck`) だけを TLC と一致させる。
- 後のマイルストーンが必要なケースは、M3 と同じく記録はするが照合では数えない。`temporal` では `-simulate` などを使う 46 件が M5 である。

## 前提として確かめた事実

- **コーパスの構成:** `temporal` は 14 の分類に 873 件ある。PROPERTY だけでなく、公平性条件 (`WF`、`SF`) を持つ SPECIFICATION、反例の形、tableau が要る式、SYMMETRY と VIEW との組み合わせを含む。
- **PROPERTY の多くは活性の検査を通らない:** `processConfigProps` は PROPERTY の連言を水準で振り分ける。状態の水準の式は初期状態の検査 (implied init)、`[]P` は不変条件、`[][A]_v` は implied action になり、時相の水準の式だけが活性の検査に回る。implied init と implied action の検査は M3 の探索に既にある。
- **基準値 (2026-11-26):** `temporal` は 173/827 で、652 件が未実装で止まる。式の `property` 文脈は 26/922、`checker` は 808/821、`standard` は 92/96 で、止まるのはどれも PROPERTY か公平性条件を持つケースである。
- **本物の食い違い 2 件:** `temporal` の `next_subscript` にある 2 件は、INSTANCE の置換を通した SPECIFICATION の Next で、トレースに出る action の位置がずれる。TLC は `Specs.addSubsts` で式を置換の節点で包み直し、その節点の位置を出す。tlars は置換を文脈に積むので、包む前の式の位置が出る。PROPERTY も同じ `addSubsts` を通るので、単位 2 で一緒に扱う。

## 方針

- DESIGN.md の決定 (式の側は `tlars-tool::live`、グラフの側は `tlars-check::liveness`、checker は検査の番号とビット列だけを見る) を引き継ぐ。
- TLC は振る舞いのグラフを disk に置く (`DiskGraph`、`TableauDiskGraph`)。DESIGN.md のとおり M6 まではメモリに置くが、出力に効く順序は写す。具体的には、辺を加える順、節点を書き直したときの位置 (`addNode` が新しい位置を返す)、`NodePtrTable` と `TableauNodePtrTable` のハッシュ表の走査順、強連結成分の探索で使う link の値である。
- 時相式の原子 (`LNStateAST`、`LNAction` など) の等値は、TLC では `tagExpr` が振った番号で決まる。同じオブジェクトを 2 度たどると後の番号で上書きされるが、別のオブジェクトが同じ番号を持つことはない。したがって原子の等値はオブジェクトの同一性と同じであり、tlars では参照の同一性で比べる。
- M3 と同じく、未実装の機能は推測した結果を返さず評価エラーとして止める。各単位の終わりに合格件数を測り、既に合格したケースが落ちないこと (`run --check`) と、本物の食い違いが 0 件であることを確かめてから次へ進む。

## 作業の単位 (危険の大きい順)

1. **照合の土台:** `temporal` と式の `property` 文脈の期待値を bc1b506 の TLC で記録し、ハーネスから M4 に回す規則を外し、基準値を測る。
2. **PROPERTY の振り分け:** `processConfigProps` (implied init、不変条件、implied action、時相の式への振り分けと、その誤りの文言と警告)、`Specs.addSubsts` の位置、`TLCGet("spec")` の `impliedtemporals`。
3. **式の側:** `astToLive`、`tagExpr`、`pushNeg`、`simplify`、DNF、`<>[]A`、`[]<>A`、`[]<>S` と tableau の式への分類、同じ tableau の式を持つ分岐をまとめる `OrderOfSolution`、particle tableau (`TBGraph`)、promise、メッセージ 2212 と式の誤り (2214 ほか)。
4. **グラフの側:** `SetOfStates` のスロット順、探索中の `addInitState` と `addNextState` (tableau なしと tableau あり、終了済みの状態を後から展開する経路を含む)、check の結果のビット列、メッセージ 2192 と 2267。
5. **強連結成分と反例:** `checkSccs` (反復版の Tarjan、`<>[]A` による辺の刈り込み、1 点の成分の扱い)、`checkComponent`、`getPath` による前半、`dfsPostFix` と `bfsPostFix` による周回、`Stuttering` と `Back to state` の表示、`findViolatedProperties`、公平性のない PROPERTY の警告、反例に対する POSTCONDITION と ALIAS。
6. **残り:** SYMMETRY と VIEW のもとでの活性の検査、統計のメッセージなど、単位 5 までで止まるケース。

単位 2 以降はスイートごとの合格件数で進捗を測り、件数の推移をこの文書の記録に残す。

## 単位 2 で残した差

- **`Specs.addSubsts` の枠の一部。** tlars は置換を文脈に積み、TLC が包み直した節点は action の位置と評価の位置の列 (2103) にだけ写す。写すのは Next の action と最初の初期述語である。2 番目以降の初期述語と、INSTANCE を通した PROPERTY から作った検査 (不変条件、implied init、implied action) は、包んだ節点の位置を列に積まない。コーパスに該当するケースはない。
