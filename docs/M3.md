# M3 計画: 状態の探索

M3 では、TLC の 1 worker の幅優先探索 (`ModelChecker`) と、それを支える `SpecProcessor` の cfg 処理、action の分割、状態と指紋、違反トレースの再構成と表示を Rust で書き、状態を持つ仕様の検査結果と TLC の出力をバイト単位で一致させる。この文書は作業の順序と完了条件を決め、進捗を記録する。

## 完了条件

- tla-ts のコーパスの次の対象について、tlars と TLC bc1b506 の終了コードと正規化した `-tool` 出力が一致する。照合は `xtask conformance run --check --suite S --context C` で行い、CI が全部の対象を流す。

  | スイート | 文脈 | 件数 |
  |---|---|---|
  | `checker` | `model` | 808 |
  | `standard` | `model` | 92 |
  | `standard` | `assume`、`init`、`next`、`invariant` | 1150、1138、1129、1138 |
  | `expressions` | `init`、`next`、`invariant` | 922、922、922 |

- 後のマイルストーンが必要なケースは、記録はするが照合では数えない。規則はハーネスの `Case::deferred_to` にあり、ケースの引数と cfg から決める。
  - M5: CLI の別モードと出力の引数 (`-simulate`、`-generate`、`-dfid`、`-continue`、`-difftrace`、`-dump`、`-dumpTrace`、`-coverage`、`-inv`、`-invlevel`、`-postCondition`、`-loadTrace`)。`checker` 206 件、`standard` 14 件。
  - M4: cfg に `PROPERTY`/`PROPERTIES` がある。`checker` 13 件、`standard` 4 件。式のケースの `property` 文脈も M4 である。
  - M6: `-workers` が 2 以上。該当は 0 件。
- 値の指紋 (`fingerPrint`) は、TLC から作った golden と一致する。M2 の完了条件に挙げていたが M2 では作っておらず、FPSet が初めて使うので M3 で作る。
- M2 から回したメッセージ 2103 (評価に失敗した式の位置の列) が、上の照合で TLC と一致する。

## 前提として確かめた事実

- **見出しの読み取りの不具合:** ハーネスは、ケースの見出しでブロック形式 (`- ` の並び) の `args:` と `flags:` を読めていなかった。`checker` の 232 件は引数なしで、`standard` の式のケース 1154 件は `model` 文脈として記録されていた。読み取りを直し、両スイートを記録し直した。M2 の `expressions` は 1 行形式だけなので影響はない。
- **`standard` の中身:** 1264 件のうち 1154 件は式のケースで、`model` 文脈は 110 件である。式のケースは `assume` 文脈なら状態の探索なしで動く。
- **基準値:** 状態を持つ対象は、評価の前に終わるケース (SANY のエラーなど) だけが合格している。`standard` の `assume` は M2 の評価器だけで 618/1150 が通る。

## 方針

- DESIGN.md の決定 (FPSet、queue、trace は M6 まで in-memory、1 worker で TLC と完全に一致させる) を引き継ぐ。disk 版と並列化は M6 で同じ型の背後に差し込む。
- M2 と同じく、未実装の機能は推測した結果を返さず、評価エラーとして止める。照合が「動いていないのに合格」を出さないためである。
- 各単位の終わりに合格件数を測り、既に合格したケースが落ちないこと (`run --check`) と、未実装による停止ではない食い違いが 0 件であることを確かめてから次へ進む。

## 作業の単位 (危険の大きい順)

1. **照合の土台:** 上の 3 つの期待値を bc1b506 の TLC で記録し、M4、M5、M6 に回すケースの除外規則を決め、tlars の基準値を測る。
2. **初期状態:** `processConfig` (INIT、NEXT、SPECIFICATION、INVARIANT、CONSTRAINT、ACTION_CONSTRAINT と、その誤りの文言)、`vars[]` と状態、`getInitStates` (`\in` の列挙、`=` による代入、未代入の検出)、初期状態の数の報告。
3. **幅優先探索:** 値の指紋 (FP64、Java の golden)、in-memory の FPSet と queue、action の分割と `getNextStates` (prime、`UNCHANGED`、`ENABLED` の定数部分)、デッドロック、不変条件、制約、進捗と統計のメッセージ。
4. **違反トレース:** trace の記録と再構成、状態の表示 (2121、2217、2218、2122)、評価失敗時の `CallStackTool` 相当の再実行と 2103。
5. **cfg の残りと TLC モジュール:** VIEW、ALIAS、SYMMETRY、POSTCONDITION、`_POSSIBLE`、`_PERIODIC`、`TLCGet`/`TLCSet`。
6. **残りの標準モジュール:** Bags、Json、Randomization、TLCExt、TransitiveClosure、RealTime、AnySet、TLCEval、Reals のうちコーパスが使うもの。

単位 2 以降はスイートごとの合格件数で進捗を測り、件数の推移をこの文書の記録に残す。

## 単位 2 と 3 で残した食い違い

本物の食い違いは 10 対象すべてで 0 件である。

- **`levelParams` (コーパスでは一致)。** 2146 の「TLC の level 検査の不具合」の但し書きは本体の `levelParams` が空でないときだけ付く (`SpecProcessor.java:1019-1022`)。グラフが `levelParams` を持たないので、tlars は但し書きなしの形を出す。コーパスの 5 件はいずれも但し書きなしなので今は一致している。
- **`getFcnContext` の複数引数の分岐。** 単一引数の定義域エラーだけ `Tool.java:3999-4004` の文言に合わせた。`plen != 1` の分岐 (`:4022-4046`) は `FcnLambdaValue.apply` の文言を使っており、コーパスには該当がない。
- **FPSet と queue の実装。** `MultiFPSet` の上位ビットによる振り分けは写したが、中身は `BTreeSet` で、disk 版と `-fpmem` の扱いは M6 である。`checkFPs` は格納先ごとの最小隣接差の最小値 (`MultiFPSet.java:153-160`) を返す。
- **単位 5 と 6 の機能で止まるケース。** VIEW、SYMMETRY、ALIAS、POSTCONDITION、ENABLED、`\cdot`、残りの標準モジュールと `TLCGet`/`TLCSet`。checker 266 件、standard の各文脈 524〜531 件。
